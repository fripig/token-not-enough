## Context

`HARD_KPI` (1.3) multiplies the KPI of Rust, App and DevOps tickets in both modes, together with a due date +1 day (`stack-agent-effects`, Harder stack compensation). It was added in `tech-stack-companies` because those stacks run slower (×1.2 / ×1.15 / ×1.25) and serial mode is limited by hours. #45 set the parallel S threshold to the strong-play median (10,700) and found that strong play gets S far more often on these three stacks.

The multiplier is applied when a ticket is created (`makeIssue`, the complexity 6 branch inside it) and when 找主管重新評估 succeeds (`rescope`). Outsourcing pay is `kpi × GIG_PAY` (`makeGig`). Day-1 tickets are generated by `firstIssues()` before the setup dialog is confirmed; the confirm handler regenerates them only when the work content changes, and sets `S.mode` after that. `tools/sim.js` also calls `firstIssues()` before assigning `S.mode`.

Measurements in this document were taken on 2026-10-11 on `main` 95f5188, in a scratchpad copy where `HARD_KPI` was edited (both modes), `SIM_N=100`, 300 games per row. Only parallel rows are used, and the simulator's parallel loop runs first, so they match a parallel-only change.

## Goals / Non-Goals

**Goals:**

- Parallel mode: Rust, App and DevOps get no KPI bonus, so strong play scores about the same on every work content.
- Serial mode: unchanged, ×1.3 stays.
- Parallel S keeps meaning "median of strong play" (#45) after the change.

**Non-Goals:**

- Due date +1 day: unchanged in both modes.
- Serial balance (serial default Rust is −76.8% vs Laravel today); not touched.
- Parallel A–D and serial thresholds.
- Outsourcing pay rate and the expensive-subscription question (#52, `gh-52-01-sub-outsource-cost`).
- The default autoplayer's ±25% parallel target for Rust; it is recorded as missed, not retuned (see Risks).
- DESIGN.md says gigs draw from laravel, rails, rust, app, fe while `GIG_STACKS` also has sre and devops; not fixed here.

## Decisions

### Parallel mode drops the hard-stack KPI bonus

A helper in `state.js` returns the hard-stack multiplier for a stack in the current mode: `HARD_KPI` when the stack is rust, app or devops and the mode is serial, otherwise 1. `makeIssue` (normal and complexity 6) and `rescope` use it instead of reading `HARD_KPI` directly. `HARD_KPI` stays 1.3.

Strong play (`SIM_SLOTS=6 SIM_INVEST=2 SIM_CONF=1 SIM_SUB=pro200`, seed 101), parallel mean vs Laravel:

| Multiplier | Rust | App | DevOps | SRE | Rails |
|---|---|---|---|---|---|
| 1.3 (now) | +22.7% | +19.1% | +21.8% | +2.4% | −0.2% |
| 1.15 | +10.7% | +7.5% | +10.0% | +2.5% | −0.2% |
| 1.0 (chosen) | −1.7% | −4.6% | −2.4% | +2.6% | −0.2% |

Default autoplayer (3 slots, seed 101), parallel mean vs Laravel:

| Multiplier | Rust | App | DevOps | SRE |
|---|---|---|---|---|
| 1.3 (now) | −13.8% | +6.1% | +12.7% | −9.9% |
| 1.15 | −23.3% | −5.1% | +1.0% | −9.9% |
| 1.0 (chosen) | −32.9% | −16.6% | −10.9% | −9.9% |

Alternatives: ×1.15 for all three (keeps the default autoplayer within ±25% but strong-play Rust and DevOps stay at +10% with three times Laravel's S share); App and DevOps ×1.0 with Rust ×1.15 (strong-play Rust +10.7%, and one more exception to explain). The user chose ×1.0 in `/spectra-discuss`.

### Due date bonus stays in both modes

With ×1.0, strong-play Rust, App and DevOps are within −5% of Laravel, so the extra day does not give an advantage worth removing, and keeping it means the rule changes in one place only.

### Outsourcing pay follows the ticket KPI

`makeGig` keeps `pay = kpi × GIG_PAY`, so parallel-mode Rust, App and DevOps gigs pay without ×1.3 (for example a complexity 2 Rust gig pays NT$1,500 instead of NT$2,000). Money does not count toward the score; a separate gig multiplier would be a second rule for the same thing.

### Recompute day-1 KPI when the mode changes at setup

The setup dialog generates day-1 tickets before the mode is confirmed, so after confirm every queued ticket must have the KPI (and gig pay) that `makeIssue` / `makeGig` give in the confirmed mode. When the work content changed, the tickets are regenerated after the mode is set; otherwise, when the mode changed, the KPI is recomputed from complexity and stack (day-1 tickets are never incidents and never complexity 6, and no investments exist yet). No random numbers are drawn. The Monday adjustment cannot change the mode, so nothing else needs this.

### Simulator sets the mode before day-1 tickets

`tools/sim.js` assigns `S.mode` before its `firstIssues()` call, so day-1 tickets match the mode being simulated. `firstIssues()` draws the same random numbers in both modes, so the only output change from this line is day-1 KPI.

### Parallel S threshold at the new strong-play median

**Supersedes**: gh-45-01-kpi-balance / Parallel S at the strong-play median

Same rule as #45 (parallel S = median score of strong play over the six work contents, rounded to hundreds), re-measured with ×1.0: median 9,525 (seed 101) and 9,558 (seed 202), so S is 9,500. Strong-play S share at 9,500: 50.8% / 52.8%; per work content (seed 101 / 202) Laravel 56.3 / 53.7, Rails 52.7 / 59.0, Rust 48.3 / 52.3, App 36.3 / 40.3, DevOps 45.3 / 48.3, SRE 66.0 / 63.0. The current code's strong-play median is 10,811 / 10,768 (complexity 6 tickets were added after #45 measured 10,700).

## Implementation Contract

**Behavior**

- Parallel mode: a non-incident complexity 3 Rust ticket has KPI 10; App complexity 4 incident 26; DevOps complexity 3 is 10. Serial mode: 13, 33, 13 as today. Due dates are the same in both modes.
- 找主管重新評估 sets KPI to `KPI[true complexity]` × the multiplier for the current mode.
- Parallel-mode Rust, App and DevOps gigs pay `KPI × 250` without ×1.3.
- Starting a game: whatever mode the setup dialog had before, after confirming, every day-1 ticket's KPI and gig pay match the confirmed mode.
- Month end: parallel S at 9,500 or more; parallel A 5,280, B 4,000, C 2,720; serial 3,800 / 2,400 / 1,400 / 500.
- Rules modal: the stack compensation line says the KPI ×1.3 applies in serial mode only and the extra day in both (zh-TW and en, same `{x}` parameter); the 結算 tab shows 9500 in the parallel S cell.

**Interface / data shape**

- New exported helper in `state.js` returning the multiplier for a stack in the current mode; `hardStack` keeps its meaning (rust, app, devops) and still drives the due date.
- `GRADES.parallel` becomes `[9500, 5280, 4000, 2720]`.
- No new save fields; `SAVE_VER` unchanged. Tickets already in a save keep their stored KPI.

**Acceptance criteria**

- `node tools/check.js` passes with 0 failures, including new assertions: KPI by stack in parallel mode (the Example table's parallel column), rescope in parallel mode, a parallel Rust gig's pay, day-1 KPI after switching mode at setup, the parallel threshold rows at 9,500 / 9,499.
- `SIM_N=100 SIM_SEED=101` and `SIM_SEED=202` with strong-play flags: parallel Rust, App, DevOps within ±5% of Laravel; strong-play parallel S share 45%–55%.
- Serial rows of the default autoplayer at seed 101 match the pre-change output within ±1% (only the simulator's day-1 mode fix differs).

**Scope**

- In: the multiplier helper and its three call sites, setup-confirm recompute, `GRADES.parallel`, rules text (zh-TW, en), simulator mode order, check tests, DESIGN.md.
- Out: everything under Non-Goals.

## Risks / Trade-offs

- [Default autoplayer, parallel Rust −32.9% vs Laravel, outside the ±25% target] → accepted by the user as the cost of using capability-30 models on Rust (Rust is ★★★); recorded in DESIGN.md.
- [Parallel default grades shift down on hard stacks] → with S 9,500 and A–D unchanged, the default autoplayer (seed 101 / 202) gets A 52.6% / 53.7%, B 30.6% / 29.8%, C 12.6% / 12.1%, D 4.3% / 4.3%, S 0% / 0.1%; current code at seed 101 is A 72.8%, B 19.4%, C 6.0%, D 1.7%. The drop is on Rust, App and DevOps (A games out of 300 at seed 101: Rust 153 → 46, App 235 → 121, DevOps 266 → 164; Laravel 236 → 216). Recorded, A–D not retuned.
- [Measurements were taken by editing `HARD_KPI` in both modes] → task 4.1 re-measures on the shipped code with the parallel-only rule and the simulator mode fix.
